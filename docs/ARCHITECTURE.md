# Architecture

## Packages

```
shared ──► client  (Vite, three.js, WebAudio, DOM HUD)
   └─────► server  (Node, Colyseus 0.18)
```

`shared` is imported as TypeScript source by both sides (Vite and tsx compile it). It holds everything that must agree on client and server: tunables, input format, movement, weapon state machine, damage, hitscan, map data, Rapier world construction, and message schemas.

## Timing model

| Loop                                | Rate                       | Where                                   |
| ----------------------------------- | -------------------------- | --------------------------------------- |
| Simulation step (movement, weapons) | 60 Hz fixed (`SIM.tickHz`) | client + server                         |
| Snapshots / state patches           | 30 Hz (`NET.serverTickHz`) | server → clients                        |
| Render                              | display rate               | client, interpolating between sim steps |

The client accumulates real time, runs whole 60 Hz sim steps, and renders with `alpha = accumulator / dt` between the previous and current sim state. Simulation is therefore independent of frame rate: deterministic for tests and identical to the server.

## Authority (M3+)

- Clients send **inputs** (sequence-numbered, one per sim step, batched), never positions or hits.
- The server simulates every player with the same `shared` code and validates inputs (rate, ranges, fire cooldown). It resolves hits with lag compensation: hitboxes are rewound to the shooter's view time, within a capped window (M3b, see Online match › Online combat).
- Local player: prediction + reconciliation (unacknowledged inputs are replayed on top of the server state). Remote players: interpolation 100–250 ms behind (adaptive jitter buffer).

### Online match (M3 movement, combat, lobbies and bots)

```
client (Game, 60 Hz)                                   server (MatchRoom, 60 Hz)
 Input.sample → sanitizeInput → stepPlayer (predict)
   └ OnlineSession.recordStep ─ flush once per frame ─► 'input' {inputs: WireInput[1..16]}
                                                         valibot InputMessageOrNull (bad → kicked)
                                                         TokenBucket 66/s, burst 30 (excess dropped)
                                                         seq > last accepted, queue ≤ 64 (oldest out)
                                                         SnapshotPacer: whole 1/60 s ticks of real time
                                                         MatchSim.step: 1 step of credit per tick
                                                           → stepPlayer (same code, same Rapier map)
 reconcile (shared/net/reconcile) ◄──────────────────── 'snap' every 2nd tick (30 Hz):
   ack'd prediction == server? keep : reset + replay      id, pos, vel, yaw, pitch, eye, flags, hp,
 RemoteTrack per remote (render t − 100–250 ms, adaptive) weapon (in hand, raising, switch time),
                                                          ack (last applied seq), life (spawn count)
   → RemotePlayersView (capsule humanoid + name tag)    'welcome' (joiner: id, map, spawn, seed)
                                                        'roster'  (join/leave/drop/reconnect)
                                                        'respawn' (that player: life, last old-life seq)
 each input also carries vt (view time, M3b) ────────► shots/strikes/frags resolved on the server
 predicted muzzle/tracer/hit marker ◄───────────────── 'combat' (shot, hit confirm + hp/killed, nade, boom)
 score line, kill feed, results ◄──────────────────── 'match'  (phase, clock, K/D per player, winners)
 'pong' {t} ─────────────────────────────────────────► ◄ 'ping' {t, rtt} every 1 s (RTT for lag comp)
 'name' {name} on Play after a menu edit ────────────────────► sanitizeName + rate limit → 'roster'
```

- **Server time and snapshot pacing (`match/pacer.ts`):** timers are only wake-ups (Node on Windows fires every timer on a 15.6 ms grid; stalls skip callbacks). `SnapshotPacer` turns each wake-up into as many whole 60 Hz ticks as real time has passed (≤ 8 per call, the rest carried; a stall beyond 1 s is skipped, not replayed), so `tick` — and the snapshot time `t × 1/60 s` clients interpolate on — follows the wall clock on any host, with the exact same fixed steps. It also aims each 30 Hz snapshot at its tick's absolute time: a busy-wait of at most 1.5 ms when the target is that close; a snapshot tick may run up to half the measured timer granularity early (≤ 8 ms; ≈ 0.5 ms on Linux) so the snapshot leaves at the nearest wake-up rather than always the next; never two snapshots closer than 0.75 × 33 ms (after a late one the next is held back instead of bunched). The granularity is learned from how late wake-ups come, so the same code paces Linux (±1 ms) and Windows (grid-bound). Measured on this PC (local production server, 20 s, 5 bots): interval p50/p95/p99/max 31.4/58–60/63–65/66–70 ms, min 4–10 ms → 31.5/45–46/47/51 ms, min 19–25 ms. (`FixedTicker` in `match/ticker.ts` remains for sim tests.)
- **Abuse limits:** every matchmaking request passes the static `MatchRoom.onAuth` first: a per-address token bucket (`rooms/matchGuard.ts`, burst 12, 1/s) and option validation, refused with a `ServerError` (answered, not logged). Live match rooms are capped (32; each builds a physics world), released in `onDispose` (which also runs when `onCreate` threw). A room nobody joined is disposed after 10 s (30 s for later joiners). The address is Colyseus's `AuthContext.ip` (first `X-Real-IP` / `X-Forwarded-For` hop): **deploy behind a reverse proxy that sets it** — without one every client shares one key (a global rate) and a directly exposed server lets clients forge it; the room cap is the backstop either way. Invalid `input` payloads kick the sender whether sent as a message or a `room.request` (the schema never fails, so Colyseus never logs the payload).
- **Rooms:** `match` (`server/src/rooms/MatchRoom.ts`) next to the `dev` wiring room. Options are valibot-validated (`MatchOptions` / `MatchSettings`). `filterBy(['lobby', 'map', 'size', 'mode'])` keeps `?online` quick join separate from explicit friend lobbies (default Plac Defilad · Market · standard). Colyseus matches on the _raw_ options, so quick join sends every matching key explicitly (`normalizeMatchOptions`; the range's only size is `full`). Friend links join the exact Colyseus room ID with `joinById`. Max six players including bots and disconnected humans reserving a seat. The room owns a `MatchSim` (`server/src/match/MatchSim.ts`, Colyseus-free and unit tested): the shared `PhysicsWorld` for the map, one `RapierCharacter` per player, input queues, the 60 Hz step and the snapshot/roster views. Spawns: the generated set (identical to the client's), the one safest from the living (`match/spawn.ts` → shared `sim/spawnSafety.ts` `pickSafeSpawn`: each living enemy with a clear sight line from its eye to a standing eye at the spawn costs `SPAWN_SAFETY.seenPenalty` (1000 m), then the distance to the nearest enemy; hard geometry only, lower index wins ties; one ray per enemy per spawn). The offline game picks the same way against a living sparring partner (dummies don't count). Falling below y = −20 respawns (`life` + 1) and sends that player a `respawn` message with the last input of the old life.
- **Input rules:** schema-valid or the sender is disconnected (the room keeps serving everyone else); `sanitizeInput` clamps ranges; stale/duplicate seqs are ignored; a token bucket drops floods before they queue. **Movement time is budgeted:** each player earns one step of credit per 1/60 s of real server time (measured, so a late timer tick catches up) and every step spends one, so nobody moves more steps than time has passed, whatever they send (a 2× input rate gains nothing; saved-up time only catches up, ≤ 8 steps per tick). When the credit is full (12 ticks = 200 ms without inputs: menu open, tab hidden, connection lost, or a client trickling inputs to hover) the server runs an idle step each tick: movement only (gravity, deceleration), weapons and kit frozen exactly like the paused client, not acknowledged, so the next reconcile corrects only the body. **Late inputs after idling are skipped:** each idle step adds one step of idle debt; when the stalled inputs finally arrive, those the budget can't cover (queue − credit, at most the debt) are dropped oldest first and acknowledged unapplied, since the server already spent that time idling. Without this the queue would drain exactly as fast as the client refills it, and a 500 ms hiccup would leave ~280 ms of input lag for good (for every viewer, and for M3b's hit checks). Jitter and a resume after a pause fit the budget and are never skipped. A full queue (64) drops its oldest input, never the newest.
- **Leave / reconnect:** a consented leave frees the seat at once (the page holds its room in `OnlineLink` and leaves on `pagehide` and before a settings reload, so a closed or reloaded tab never leaves a ghost for 20 s); a dropped socket keeps the seat and body for 20 s (`allowReconnection`, the SDK reconnects on its own into the same session); a kick (invalid payload, message flood) frees it immediately. Roster broadcasts carry `connected`. The client retries the seat however soon after joining the drop happens (`reconnection.minUptime = 0`) and holds the local player still whenever it is not in the match (joining, reconnecting, or offline for good; nothing done meanwhile could reach the server). Inputs not yet sent when the socket drops are discarded (never delivered late). On reconnect it drops every prediction made before the drop (inputs in flight may never have arrived) and remembers the state it resumes from, so the first snapshot after reconnecting rebuilds on that state with the server's movement and replays only newer inputs, each exactly once — also when the server has not applied any input yet (`ack` = −1, M3b fix): ack-less snapshots are compared with the spawn/last authoritative baseline, because incoming damage and idle movement can change the server state before it applies any input. Reconnect always rebuilds that baseline and discards pre-drop predictions. A server respawn re-aims the camera to the new life's heading. A respawn that happened while away is resent on reconnect.
- **Prediction:** the client steps itself with the sanitized input the server will step, keeps each step's predicted state until acknowledged, and on each snapshot compares the acknowledged prediction with the server's state (position, velocity, grounded/crouched/climbing, weapon in hand and switch timer, since the knife runs faster; health; the climb/vault in progress; and, in the recipient's own entry only, its weapon and kit state). **Traversal on the wire (M3b fix):** a climb/vault carries its whole fixed path (`tr`: kind, duration, start, waypoints, end, direction), so one the server started but the client never predicted (a ledge it missed, an input it never had) is rebuilt exactly and replayed along. **Own weapon/kit state (M3b fix):** each client's snapshot carries in its own entry (`own`) the complete numeric gun state (ammo, reload, cooldown, spread/recoil, ADS and buffered triggers), frags/smokes/jammers, the hands (stun, counter, guard, throw kind and swing combo/phase/timers), movement timers and previous input buttons; a differing count forces a rebuild, so a Fire or Grenade the server skipped (late after a stall, lost in a reconnect) or a stun it applied never leaves the client's counts wrong for good (a throw the server never started is called off: no phantom frag). Equal (the normal case: same code, same map, same floats) → nothing happens. Different → reset the movement fields, health, weapon in hand and own weapon/kit state to the server's and replay every unacknowledged input through `stepPlayer`, moving the Rapier body with it (`RapierCharacter.setGrounded` restores ground contact). The acknowledged step stays as the reference for the next snapshot, which often repeats the ack (30 Hz snapshots, 60 Hz inputs). A `respawn` message rebuilds the new life on a fresh spawn state and replays every input after the old life's last one (some of which the server may already have applied); a snapshot from an older life is ignored. Guarded by `server/src/rooms/MatchRoom.test.ts` (a predicting client over the real transport: zero corrections) and `match/MatchSim.test.ts` (server == client bit-for-bit on the range and the Market).
- **Remote players:** a `ServerClock` estimates server time from snapshot arrivals (follows the fastest arrival, slews slowly towards later ones), and each remote player is sampled in the past between two real snapshots: positions and eye height blended, yaw on the short arc, flags/health from the nearer one, never blended across a respawn. **Adaptive jitter buffer** (`JitterBuffer`, `client/net/interpolation.ts`): the delay is `clamp(100 ms, 33 ms + 1.5 × lateness peak, 250 ms)`, where lateness = how much later than the fastest path a snapshot arrived; the peak jumps on a late snapshot, grows with the silence during a stall, and decays over ~4 s; the delay in use rises at most ½ ms per ms (remote time slows, never runs backwards) and falls at 2 %. Past the newest snapshot (a stall) a player moves on its last velocity for ≤ 150 ms (`maxExtrapolateMs`; never the dead, never a fall), then holds; when data resumes, `RemoteTrack` turns the difference at that instant into an offset that decays (50 ms time constant, gone in ~150 ms) instead of snapping (> 6 m or a respawn snaps). **Lag compensation stays honest:** each input's `vt` is exactly what was drawn (server now − the adaptive delay), and the server clamps each player's rewind to the buffer's ceiling + the round trip it measured itself + a margin, never past 350 ms (see Hitscan with lag compensation), so what is drawn is what is checked up to ~60 ms of ping with the buffer at its ceiling and ~200 ms with a clean one. Beyond that the shooter must lead by the excess; remote players look smooth instead of freezing and teleporting. Replay of a recorded match through a tunnel-like delay model (1 s stall + frequent 70–190 ms stalls): frozen-while-moving frames 4.0 % → 2.0 %, per-frame jumps > 0.3 m 6 → 6 (worst 4.4 → 1.3 m), mean error vs the true path 0.056 → 0.028 m. **Local corrections** (`client/net/correctionSmoother.ts`): the sim adopts the server's state at once (prediction stays exact); the camera keeps drawing where it was and the difference decays (35 ms time constant, ~95 % gone in 100 ms); > 2 m or a respawn snaps. **HUD:** `PING n ms` under the status badge (green < 80, amber < 150, red), with `JITTER` / `UNSTABLE CONNECTION` / `NETWORK STALL` when snapshots jitter, keep stalling or stop (`net/netIndicator.ts`; not blamed on the network while the page itself hitches). Figures are pre-built per slot (compiled by `Game.warmUp`); name tags are depth-tested and shown only when the player passes the shared sight check (walls, smoke and foliage hide them), so tags never reveal hidden players.
- **Online combat (M3b):** clients send only inputs (Fire, Knife, Grenade are buttons). The server's `stepPlayer` runs the shared weapon/arsenal state machine, so **fire rate, ammo, reloads, the semi-auto cycle and one frag per life are enforced by the same code** whatever a client sends (inputs are rate limited and movement-time budgeted, so a faster input stream fires no faster; `sanitizeInput` clamps pitch and wraps yaw). Each tick first steps all players and captures their combat intents with the state at each release, then resolves damage. Queued return fire cannot disappear because the shooter was killed earlier in player iteration order. Its `shot`, `melee` and `grenadeThrow` events are resolved in `MatchSim`:
  - **Hitscan with lag compensation** (`match/lagComp.ts`): every player's pose (feet, eye height, life, alive) is recorded at spawn and each tick in a `PoseHistory` (30 ticks). A shot is traced with the shared `traceShot` against the other players' `humanoidHitboxes` **rewound to the shooter's view time**: the `vt` each input carries (the client's server clock − its adaptive interpolation delay: the time it was drawing the others at), or without one interpolation delay + RTT. **The rewind cap is per player (Kiran, 2026-09-30):** `vt` is clamped (never rejected) to `[now − rewindCapMs, now]` with `rewindCapMs = min(maxRewindMs 350 ms, interpolation delay + RTT + rewindMarginMs 40 ms)`. An honest shot asks for its interpolation delay + the _whole_ round trip + 6–12 ms of queueing (measured: the client's server clock follows snapshot arrivals, one trip behind, and the input takes another trip). The RTT is the server's own (`RttEstimate` from its 1 s `ping` → `pong`; never a client-reported number). A pong only counts if it echoes the exact stamp of a ping the server sent that player and that is still outstanding, once (`PingTracker`: forged, replayed and > 5 s late echoes are ignored; at most 8 outstanding), so a client cannot invent samples, only answer late. The cap uses the 90th percentile of the last 10 samples, so one spike — or a client sitting on one pong — never widens the cap (an EWMA would leak a quarter of each spike for seconds), while a real rise shows within two samples; a client can only make its ping look longer, which the ceiling bounds. The server cannot see a client's jitter buffer, so the interpolation delay is granted up to the buffer's ceiling (`maxInterpDelayMs` 250 ms): the cap is 290 ms + RTT, i.e. the 350 ms ceiling from 60 ms of ping. So nobody reaches further back than 350 ms whatever they report or however they ping, a low-ping client lying about `vt` gains at most what an honest one with a stalled buffer gets, and beyond the ceiling (≈ 240 ms RTT on a clean link, less after a stall) the shooter has to lead. The pose history (30 ticks, 500 ms) and the spent-smoke history cover the ceiling. Poses are blended between ticks like client snapshots, never blended across a respawn or a death; the old life is held until the respawn timestamp, matching client interpolation. A player dead now, or respawned since the view time, can't be hit. Damage = shared `computeDamage` (zone, range falloff).
  - **Knife** = shared `resolveMelee` (inflated hit volumes, rewound the same way) + `applyKnifeStrike` using the attacker's release pose/counter bonus against the defender's guard now (block, guard break; a parry stuns and shoves the attacker, which reaches the attacker through its own snapshot state). **Frags** fly on the server with the shared `spawnGrenade`/`stepGrenade` (thrower's seed) and blast with `explosionDamage` (blocked by any solid between blast and chest; self-damage counts, no kill credit for yourself).
  - **Deaths and respawns:** at health 0 the dead don't act (`stepPlayer` returns early everywhere: server, prediction, replays); kills/deaths are counted; respawn after `MATCH.respawnDelay` (3 s) at the generated spawn safest from the living (see Spawns), with a `respawn` message as for a fall.
  - **Spawn protection** (`shared/sim/spawnProtection.ts`, `SPAWN_PROTECTION.duration` 2 s): every spawn (join, respawn, new match; a still-loading joiner gets it afresh when it enters the fight) grants `PlayerState.spawnGuard`. `MatchSim.damage` blocks everything while it lasts (bullets, knife before `applyKnifeStrike` so no parry/guard wear, frags, one's own frag) and reports a `hit` with `dmg` 0 and `outcome: 'protected'`. It ends in `stepPlayer` on the step of a shot, a knife swing's start or a throw's wind-up (before they resolve, so a protected player never attacks); ADS, reload, sprint, switching, the guard, a coil charge and a dry trigger keep it. The server expires it by its own clock (`ServerPlayer.guardEndsTick`, checked every tick after the player's inputs and before hits resolve: `spawnGuard` is derived purely from it unless an attack ended this life's protection (`guardBroken`), so a batch of inputs neither shortens nor stretches the 2 s); the client predicts it with `stepPlayer`'s countdown and adopts `own.sg`. Offline the first life is protected too (granted before Play; the paused sim doesn't count it down). Judged at resolve time, not rewound (protection only runs down within a life; a shot from before the target's respawn misses by life anyway). Wire: `SnapFlag.Protected` in every entry (shimmer on soldiers via their own material's emissive colour, no new program; blocked marker predicted from it; each own shot remembers which marker it predicted, hit or blocked, and the server's confirm is deduped only against the same kind), the seconds left as `own.sg` (HUD chip); on/off disagreement forces a correction, the timer alone never does. Bots track a protected target but hold fire/swings/throws and prefer anyone hittable (`BOT.protectedPenalty`).
  - **Match flow:** FFA, first to the host's `scoreLimit` (default 25) or `timeLimit` (default 600 seconds); either may be `'unlimited'` (never auto-ends by it; with no clock `endsAt` is null), and a friend room's host can send `end {}` for the normal results (quick-join rooms refuse it). `matchWinners`: most kills, then fewest deaths, still level = a shared win (Kiran), including zero-kill games. All damage in one tick is resolved before checking the score limit, so a winning blast damages every exposed victim and same-tick trades can share the win. Results for `MATCH.intermission` (10 s), then a fresh match (scores reset, everyone respawns). During results the shared hands state still advances identically to client prediction, but no authoritative shots, throws or damage are emitted and all live frags are cleared. A `match` message goes out on every score/phase change and to each joiner.
  - **Client:** own shots draw muzzle, tracer and a **predicted hit marker** at once (other players are hit targets where they are drawn, the same place the server rewinds to). Gun `hit` confirms echo the firing input sequence; the client tracks whether that shot showed a predicted marker and supplies a confirmed nonlethal marker when it did not. The server's `hit` confirm brings the kill marker, damage number, knife defense cues, the victim's damage arrow and death banner, and the kill feed (texts in `net/combatFeed.ts`, DOM in `OnlineBadge`). **Health, kills and deaths only ever come from the server** (snapshot `hp`, `match` scores); local practice targets are absent online, and no local explosion can change health or kills. Other players' shots (`shot`) and everyone's frags (`nade`/`boom`, including your own) are drawn from server events with existing effects. On join or reconnect, the server resends active frags as `nade` events with their current pose, resting state and remaining fuse; the client refreshes known grenade IDs without duplicating meshes. The throw animation/audio is predicted immediately; live frags and their explosions wait for authority, preventing phantom blasts after a skipped throw. Results clear live frags. A temporary grenade is compiled and removed during `warmUp`, so its shared material is ready before play. The sparring partner is off online. Smoke and radar uplinks are server-owned (see M3 tactics below); local-only recon drones and jammer controls are unavailable online. Players do not collide with each other (characters only query static geometry on both sides), so prediction never depends on other players.
- **Client entry:** Menu › Match › "Play online" (reloads) or `?online` (`?online=0` off) — the URL flag applies to that page only and is never saved as the default (`onlineToSave`; only the checkbox persists); `?server=host:port` (a bare host takes the page's scheme, so https pages use wss; default: this host, port 2567 in development; the page origin in production); name from Menu › "Your name online". **The page joins at the first Play (M3b fix)**, not at load, so the room hears the name the player chose (`OnlineJoin`; `?autotest` joins at once); a later edit is sent on Play/resume as one `name` message (not once per keystroke, which would exhaust the rename bucket) (cleaned client-side, then `sanitizeName` again on the server: printable, ≤ 16 chars; burst 3, then 1 per 5 s; a malformed one kicks) and rebroadcast in the roster. The client treats its own roster name as the acknowledgment, keeps the latest desired name queued, and retries an unacknowledged rename after the 5 s bucket refill so rapid edits converge without another Play. Single-player never creates the session, the remote view or a socket beyond the M0 dev ping.

### M3 lobby and settings

`rooms/lobbyState.ts` owns the human roster and host. The first human becomes host; an unconsented drop reserves that seat and host ownership for the existing 20-second reconnect window. A final leave transfers host to the oldest remaining human. Only that host can send validated `settings` patches or `start`, and both are refused after start. No match clock, player movement or combat runs while waiting. Map construction waits until settings are frozen. Join options on an existing room never change its settings.

The shared settings contract is map (`defilad`/`range`), size (`market`/`full`/`north`/`south`), mode (`standard`/`knife`), weather (`sunny`/`overcast`/`rain`/`dusk`), radar (`uplinks`/`off`), bot count (0–5, default 5), bot behaviour (`ffa`/`hunt-humans`), difficulty (`easy`/`normal`/`hard`), score limit (1–100 or `unlimited`, default 25), and time limit (60–3600 seconds or `unlimited`, default 600; menus offer 10/25/50/Unlimited and 5/10/15/20 min/Unlimited). Range normalizes to full. Settings have one authoritative server representation; the client maps `uplinks` to the existing practice-menu `pickups` label only at its UI boundary.

`client/net/friendLobby.ts` handles create/join and the waiting screen before `Game.create`, so a friend's saved practice map cannot determine the room's geometry. The lobby shows the share link, roster and host controls. It hands the existing socket and buffered authoritative messages to `OnlineSession` after start; late joiners go directly into the running match. `?online` still joins at Play with the existing prediction/reconnect/name flow. Online settings cannot change the server's frozen map, weather, radar or mode locally.

### M3 bot decisions and the M6 boundary

`server/src/bots/` contains `DecisionProvider`, the seeded behaviour-tree baseline, filtered observations and a cached navigation graph built from the map's shared physics. `match/bots.ts` manages seats and queues each decision with `MatchSim.receiveInputs`; all bots pass through the same `sanitizeInput`, sequence/rate/time-budget checks and `stepPlayer` as humans. They share kit, ammo, damage, respawn and score rules. A decision receives copied self/public observations, never a live player state, character body or simulation. M6 can replace the provider without adding an alternative movement or combat path; no Jev dependency is installed.

Perception uses `sightVisibility` and `SIGHT_THRESHOLD`, including static walls, server smoke and the map's `FoliageIndex`. Only visible opponents enter the decision interface; unseen opponents are represented only by the bot's previously observed, expiring memory. Bots receive no hidden target health and no synthetic radar pings. Static navigation knowledge is allowed. Difficulty controls reaction, turn rate and aim error; decisions cover seeking, engaging, strafing, reloading, retreating toward cover, close knife use and occasional frags. Navigation and unstick actions produce movement/jump inputs, never player teleports.

The baseline graph samples ground-level walkable space, with a 2 m Market grid and coarser cells for larger sections. All ten Market spawns connect in the tested graph. Upper floors, ladders and authored vault routes are not explicit navigation edges yet; those routes and unstick feel need playtesting. Cached topology contains no live physics-world reference; line-of-sight wrappers belong to each room's world.

The bot count is a maximum number of filler seats, clipped to `6 - human seats`. A late human replaces a bot, a departed human makes room for a replacement, and disconnected reserved human seats are not taken by bots. Zero humans removes all bots. Bot IDs and an optional `bot` roster flag travel through the same snapshots, scores and remote-player rendering as everyone else; the client labels them `[BOT]`. Hunt-humans changes target selection only: shared FFA damage and scoring still apply, including accidental friendly damage and the existing shared-win tie rule.

### M3 shared tactics

`match/tactics.ts` owns radar charge/pickup state and smoke clouds. Smoke is released by the ordinary shared arsenal input event, flies on the server and produces a cloud when its fuse ends. `nade`/`boom` carry the grenade kind, including on reconnect, so clients render the correct event without predicting a second cloud. Each recipient's snapshot includes the same smoke clouds and uplink cooldowns plus only its own radar state. Bots and clients use those clouds for sight checks. Pickup races have a deterministic order; a stored radar charge reveals opponents only when the player presses Radar. Radar-off removes online radar uplinks. Recon drone flight and jammer effects remain practice-only until they have server authority; bots do not get their information.

### Weapon drops (Kiran, 2026-10-17)

`shared/sim/weaponDrops.ts` owns the deterministic drop list and ammo/swap rules. Standard-mode deaths drop only a nonempty primary, at ground height beneath the death position. Drops last 30 seconds; the 24-slot cap evicts the oldest. Ammo is a fraction of the source gun's magazine plus maximum reserve. Walking over it transfers whole rounds of that fraction of the current primary's full load into reserve, preserving any fraction not taken. A completely empty primary instead swaps to a nearby gun with ammo. Bots only drop; they never collect. Empty ground guns remain available to E, but empty held guns are discarded on swaps.

`MatchSim` owns the list for online and worker-based practice. After movement, truck seats have priority over an E swap. Automatic collection runs once per match tick after combat, excluding players who manually swapped that tick; on following ticks their old gun is an ordinary pickup. The existing snapshot `pr` and own weapon/arsenal state carry the changed primary and ammunition. `snap.drops` carries the bounded ground state; `drop` events provide feedback. `OnlineSession` predicts through the same shared functions and restores authoritative drops before replaying pending inputs. Respawning still uses the chosen loadout.

`WeaponDropView` prebuilds every primary in a fixed pool before warm-up, reuses soldier scan geometry, and draws one mesh per live drop. The subtle emissive pulse and final two-second fade only change material values. All variants are exposed for both compilation and real warm-up draws. All primary viewmodels were already preloaded; Low now limits their uploaded textures to 512 pixels before warm-up. Existing gun/arms files total 4,857,791 bytes (4.63 MiB), with no additional requests. Estimated RGBA8 texture storage with mipmaps is 147.27 MiB at full resolution and 31.52 MiB on Low; actual startup milliseconds and GPU performance need the browser probe below.

Proximity checks also run while standing. Taking an empty gun with E while leaving a loaded gun at your feet therefore triggers the normal empty-primary auto-swap on the following tick. No owner immunity or pickup grace period is added.

Autotest pages expose `__wd.drops()` and `__wd.dropGun(primaryId, x, z, ammoFraction)`. `__wd.gunLoadStats()` reports startup load milliseconds, decoded geometry bytes, estimated mipmapped texture bytes, gun count and the Low texture choice. The spawn hook goes through validated authoritative messages in practice and online; online servers accept it only in development. Offline range pages create the drop locally. The list is predicted client state, corrected by snapshots. No browser/GPU probe is run by the implementation lane: the lead must verify drop grounding, the prompt and truck priority, first/third-person gun switches, fade/highlight, and stable program counts across every primary after warm-up on Low/Auto.

### M3 hosting and verification boundary

### Soak and fairness harness (`pnpm soak`, `server/src/soak/`)

The M3 criterion "6 clients play a full match at 100 ms and hits feel fair", measured.

- **Clients** (`soakClient.ts`) are the browser's online loop without rendering: the client's own `OnlineSession` (prediction, reconciliation, jitter buffer, view time; DOM-free, imported from `client/src/net` — the server tsconfig references the client project), the shared `stepPlayer`, and `traceGunShot` (shared; `Game.fireShot` uses it for the predicted hit marker too). The server's behaviour tree moves them from what the client _draws_ (remote players interpolated at its `vt`); the script aims at the torso centre of the nearest visible body as drawn (ADS taps every 0.3 s), every 4th shot 0.7 m beside it. Each shot is traced locally against the drawn bodies (the predicted marker) and matched with the server's `hit` confirm by input seq 1.5 s later. **Hit-confirm rate** = confirmed / predicted hits on dead-centre shots (≥ 95 %); **false hits** = deliberate misses the shooter saw clear that the server hit (≈ 0). Shots in a death race (shooter or target killed −300..+500 ms), near a phase change or in the first second are left out and counted. Mispredictions = corrections that moved a living player (damage-only, death and respawn corrections are counted separately).
- **Real run:** one worker thread per client (Colyseus SDK) → a TCP latency proxy in its own worker (`latencyProxy.ts` + `delayLine.ts`: one-way delay ± uniform jitter per chunk, **never reordered** — the game is WebSockets over TCP, so jitter bunches deliveries; "loss" = +200 ms retransmission with head-of-line blocking, since TCP never loses a message; deliveries within 20 ms are awaited with `setImmediate` because Windows timers fire on a 15.6 ms grid: lateness p99 < 1 ms) → the production server forked as its own process (`serverProcess.ts`: probes for tick cost, wake-ups, snapshot cadence, drift, event-loop delay, input drops/skips and the rewind each shot asks for). A friend lobby with score limit 100, so `--full` plays the whole 10 min time limit; `--quick` uses quick join.
- **Virtual run** (`--virtual`, and the gate test `soak.test.ts`): the same clients against `MatchSim` stepped exactly like `MatchRoom` on a 1 ms virtual clock with seeded links: deterministic, independent of host load (a 10 min 6-client match in ~75 s).

**Findings with the flat 200 ms cap (2026-09-30, 100 ms RTT, Market, AR-7) — what led to the per-player cap:**

- Clean link: fair. Virtual 10 min × 6: hit confirm 98.1 % (757/772), false hits 0/415, mispredictions 0. Real sockets, 45 s quiet host: 98.3 %, 0 false hits, 0 mispredictions.
- **The 200 ms rewind cap is already reached at ~90 ms RTT.** Measured server-side, a shot's `now − vt` = interpolation delay + the _whole_ RTT + 6–12 ms (input queueing): `ServerClock` follows snapshot arrivals, so the client's server clock runs one-way latency behind, and the input takes another one-way to arrive. At 100 ms RTT that is 206–212 ms, so 83–90 % of shots are checked 6–12 ms later than drawn (harmless at dead centre). The docs' assumption (interp + RTT/2) is off by RTT/2. Virtual sweep, 6 clients × 120 s: hit confirm 99.5 / 99.5 / 85 / 76 / 57 % on the range and 98.7 / 96.5 / 61 / 50 / 39 % on the Market at 50 / 100 / 150 / 200 / 250 ms RTT, with false hits rising to 4–10 % at ≥ 150 ms; the loss is all on moving targets.
- **Host stalls make it unfair at 100 ms.** Full real match (10 min, 6 clients, busy laptop): overall 91.3 % (674/738), false hits 0.5 % (2/364), 0.33 mispredictions/min per client, 0 errors. Split by the shooter's interpolation delay: 97.0 % (624/643) at 100 ms, but 25–42 % after a stall (server wake-ups up to 338 ms, snapshot gaps up to 650 ms) raised the jitter buffer to 150–250 ms: then `vt` lags 250 + 100 ms and the 200 ms cap cuts 50–150 ms, i.e. 0.4–1.1 m at sprint speed. Fixed by the per-player cap below.

- Shots over their cap: none up to 150 ms, 1.4 % at 200 ms (Market), all at 250 ms (asked 358–365 ms against the 350 ms ceiling: 8–15 ms late, still 95–100 %). 11–12 mispredictions (≤ 0.11 m, ~1/min per client) appear at ≥ 200 ms RTT with either cap: not investigated.
- Full real match, 10 min, 6 clients, 100 ms RTT, Market (a quiet host this time: frame gaps p99/max 31.6 / 85.8 ms, server wake-ups max 29 ms, snapshot send interval p50/p95/max 33.2 / 37.1 / 70.0 ms, 60.00 ticks/s): hit confirm **99.4 %** (793/798; by target speed 100 / 99.7 / 100 / 98.9 / 98.4 %), false hits **0/433**, mispredictions 0, errors 0, 0 of 2170 shots over their cap (asked p50/p95/max 211 / 218 / 244 ms) → PASS (was 91.3 % / 0.5 % on the busy host with the flat cap). The stall case (buffer at 150–250 ms) did not occur in this run; its arithmetic is covered by `lagComp.test.ts` (a stalled buffer fits the cap up to ~60 ms of ping; above that the shooter leads by the excess over 350 ms).

**With spawn protection, soft-push collision and slide (main, 2026-09-30):** the headless client mirrors `Game`'s online loop: `placeBodyAt` + `grantSpawnProtection` at the welcome (the session grants it at each respawn), `stepPlayerInCrowd` against `OnlineSession.crowd()` (the reconcile replays take the same crowd), and the shot trace marks bodies drawn spawn-protected (`snapshotProtected`) as blocked, like the blocked marker. A fan (shotgun) strikes several bodies under one seq and the server answers per body in any order, so a shot is four sets (`soak/shotVerdict.ts`): bodies the local trace hit, bodies it hit drawn protected, bodies the server damaged, bodies it blocked on. `shotVerdict` puts every body in one class: damage on a predicted hit = confirm; a predicted hit neither damaged nor blocked = unconfirmed; damage on a body the trace never struck = false hit; everything protection explains (a body drawn protected whatever became of it, a predicted hit answered with `outcome: 'protected'`, a block on a bystander) = exempt. A shot with nothing but exempt outcomes is "blocked": left out of hits, misses and false hits and reported on its own line (drawn / blocked by the server / both / drawn protected but damaged); the hit-confirm rate counts the aimed-at body only when its own outcome is not exempt. Like a player, the script never fires at a shimmering body. Corrections that move a living player are split by whether another player was within 1.2 m in the last 0.6 s: away from others they are mispredictions (0 on a clean link); in contact they are expected, because each side resolves the push against the other as of its own newest snapshot and the replay of the unacknowledged inputs carries the difference.

- Virtual, Market, 6 clients × 120 s at 50 / 100 / 150 ms RTT: hit confirm 99.4 / 100 / 98.0 %, false hits 0, mispredictions 0, no contact, no shot at a protected body, nothing over the cap. Fairness is unchanged by protection and collision.
- Range (`soak.test.ts`, 4 clients × 90 s, players meet head-on): 100 % confirm at 100 and 150 ms, 0 mispredictions away from others; in contact 9–10 corrections, median 3–6 cm, largest 0.59 m at 100 ms (a head-on sprint bump: the acknowledged step was ≤ 3 cm / 0.6 m/s off, the replay of 7 unacknowledged steps carried it) and 0.15 m at 150 ms.
- Real sockets, 6 clients, 100 ms, 60 s: 98.8 % (80/81), false hits 0/37, errors 0; one host stall (frame gap 441 ms, snapshot gap 531 ms) raised the jitter buffer to 250 ms and caused 13 stall mispredictions (≤ 0.52 m), yet the 11 shots fired with the buffer at 110–200 ms were all confirmed and 2 of 213 shots were over their cap: the stall case the flat cap failed.

### Vehicles (armored trucks)

```
client (driver)                                     server (MatchSim)
 stepPlayer: seat.motion ← stepVehicle(input)        same stepPlayer, the seat holds the truck's
   (same code, own Rapier world, env obstacles)        own motion object (MatchVehicles.bindDriver)
 recordStep → inputs ───────────────────────────────► Interact / SwitchSeat edges → seatInput
                                                      driverless trucks roll (handbrake), crew ride,
                                                      run-overs, hull hits, blasts, wreck/respawn
 reconcile: own.vm vs predicted motion ◄──────────── 'snap': vehicles[] (motion, hp, state),
 VehicleTrack: others' trucks on the draw timeline     players' vh (seat), own.vm (driver)
```

- **Prediction:** only the driver predicts a truck (its motion is part of the driver's state; snapshot `own.vm`, compared by `motionError`). Everyone else interpolates trucks on the remote-player timeline (`client/net/vehicleTrack.ts`), and a passenger's camera and shots sit in that drawn truck, which is where the server rewinds it for those shots (`MatchVehicles.seatEyeAt(viewMs)`). Walkers and drivers meet the trucks as of the newest snapshot (`OnlineSession.vehicleEnv`), like the crowd: exact for parked trucks, contact corrections for moving ones.
- **Lag compensation:** each truck's pose is recorded per tick (`VehicleHistory`, 30 ticks) and its hull rebuilt at the shot's view time (same clamp and cap as players); occupants are ordinary rewound targets (their recorded pose is the seat). Same-truck crew are excluded from each other's targets.
- **Map placement:** `MapDefinition.vehicles` (two spawns on the Market's west forecourt, under the Palace); `vehicleSpawns` in `MatchConfig` overrides them for tests. Drive graph (`sim/vehicles/driveGraph.ts`) for bots and the routes test.

## Physics

Rapier (`@dimforge/rapier3d-compat`, WASM inlined; works in Node and the browser). Static map colliders are built from map data. Players are kinematic capsules moved by Rapier's `KinematicCharacterController`. Movement is split into:

1. `computeVelocity` — pure, no WASM, unit tested.
2. `RapierCharacter` — collision resolution in two passes (horizontal collide-and-slide, then vertical with snap-to-ground), plus an explicit step-up (sweep up → forward → down, accepted only onto walkable ground ≤ `CHARACTER.stepHeight`). Rapier's built-in autostep is disabled: it fails at low speeds.

Hit volumes (head sphere, torso and leg capsules) are analytic shapes in `shared/sim/hitbox.ts`, not physics colliders, so the server can rewind them cheaply for lag compensation. Rapier only answers static-world rays; `WorldHit.visible` marks collision-only geometry (bounds, stair ramps) so no decals appear on it.

## Client layers

`Game.frame` → `Input.sample` (60 Hz) → `stepPlayer` (shared) → events (shots → `traceShot` → damage / effects / HUD / audio) → render.

Mouse look is applied on every raw pointer event, so the camera turns at display rate; the sim samples the current view each step.

## Render pipeline

```
Load (Game.create, before warmUp):
  public/tex/<surface>_*.jpg (Low: _512) ─TextureLoader─► MapMaterials (swap, initTexture)   fallback: procedural
  public/env/<id>.hdr ─HDRLoader─► PMREM (cube 128) ─► EnvironmentLibrary by preset    fallback: sky bake
Weather preset ─► sun / hemi / fog / wetness uniform / rain / lightning / bloom
             └──► scene.environment = HDRI (scaled to the sky's brightness) or PMREM(sky dome)
                  (IBL for world + viewmodel; the visible sky dome is always procedural)
Low:     world → clearDepth → viewmodel                         (renderer AgX tone mapping)
Medium+: RenderPass(world) → [N8AO, High+] → ClearPass(depth) → RenderPass(viewmodel)
         → EffectPass(CAS, bloom, AgX, vignette) → EffectPass(SMAA)
```

- The viewmodel renders after AO (no AO halos on the gun) but before bloom (the muzzle flash glows).
- Map geometry is merged per material and spatial chunk, with world-metre UVs. Every surface starts
  with procedural PBR maps (albedo, normal, roughness generated at load) and a shared `uWetness`
  shader hook, so the map always draws. Nine surfaces (asphalt, sidewalk, paving, concrete, plaster,
  wood, metal, container, grass) then swap in scanned CC0 sets (`render/surfaceTextures.ts`; built
  by `tools/assets/build_textures.py`, AO in albedo, roughness in G) with per-surface tile sizes in
  metres. Each albedo is re-tinted to its surface's palette colour (materials.ts) and exposed onto
  it offline, in float before the 8-bit encode (luminance carries the detail, a scan's own chroma
  variation is kept at `CHROMA_KEEP`), so a dark or tinted scan never gets per-channel gains that
  stretch its JPEG noise; at run time one grey luminance gain through `material.color` (stats in
  `surfaceTextureStats.gen.ts`, ~1 for the committed JPEGs) absorbs later palette brightness
  tweaks. A palette hue change needs a texture rebuild (a test checks the committed hue). The
  1024 px sets also ship 512 px copies; the tier resolved at load picks them for Low (for the
  session: no uploads in play), so Low costs what the 512 px procedural maps did. A set that fails
  to load (or times out) keeps its procedural maps with a
  `console.warn`. Base materials and every `variant()` clone are updated, and grid mode swaps
  against whichever albedo is active.
- Props use 32 m instance batches and prebuilt far geometry beyond 45 m, with 6 m hysteresis.
  Crates and Jersey barriers retain their exact visible mesh at every distance because their
  openings agree with shot collision. Nearby cover casts inexpensive box shadows; small dressing
  and distant props do not cast. Simplification runs under the asset-loading deadline before warm-up.
- Trees and concealment clumps use 96 m chunks. Far trees retain the near crown's smooth,
  leaf-textured opaque geometry; decorative cards dither out over 30–42 m before the chunk swaps
  LOD, avoiding a silhouette jump or duplicate draws. Bushes use a closed concealment core with
  overlapping domed lobes. Bushes and grass retain their opaque cores at every LOD and quality.
  Low draws only opaque geometry, with no alpha test in colour or depth; Medium+ adds a bounded
  set of larger leaf cards. Clumps do not cast shadows, and tree casting is limited by distance.
  Merged clump vertices carry each plant's root/radius so wind stays local.
  Budget active colour-pass submissions separately from resident LOD meshes: each tree chunk
  has at most five resident meshes but three active draws (trunks plus one LOD per crown kind),
  and each clump chunk has two resident meshes but one active draw. Full Defilad currently has
  40 tree chunks and 38 clump chunks: 264 resident meshes, 152 active draws before frustum
  culling, below the 158 bound (`3 × tree chunks + clump chunks`). Shadow draws are separate.
  Far clump buffers contain only referenced opaque vertices; their indexed triangles and all
  vertex attributes match the near opaque geometry exactly, preserving concealment while
  avoiding about 10.5 MiB of unused decorative attributes on the full map.
- Facade relief selects indices per cell using distance and the camera frustum, while a separate
  flat wall proxy keeps shadows independent of visible relief. Shared edge vertices seal front
  quad T-junctions without overlapping coplanar faces. The shell uses dedicated pale sandstone
  maps without painted windows or scanned plaster mottling; distant panels retain painted windows.
  Palace portico and hall columns reuse the window-free shell, with unchanged collision dimensions.
- Low removes world PMREM and normal-map sampling. Weather folds the preset's mean sky irradiance
  into the existing hemisphere light; the viewmodel keeps its environment. Low's smoothstep depth
  fog approximates the exponential curve within 3.6 percentage points without vertex interpolation
  over large floor triangles. Fog does not control wetness or the sky (`fog: false` on the dome).
  Dry materials skip the wetness normal calculation. Low/Medium shadows use one hardware-filtered
  PCF sample instead of the five-sample disk, at 512/1024 px; High/Ultra retain the disk filter and
  2048/4096 px. The filtering branch is a uniform, so Medium/High do not change world programs.
- F3 reports total and shadow triangles/draws separately, plus the current program count.
  `__wd.state()` exposes `triangles`, `shadowTriangles`, `drawCalls`, `shadowDrawCalls`, and
  `shaderPrograms`. Shadow counts are CPU deltas around the existing shadow render, with no GPU
  query or additional render. Totals include the inexpensive invisible shadow proxies.
- **No shader work in play:** textures, lightmaps and HDRIs load, upload (`initTexture`) and prefilter before
  `Game.warmUp`. Warm-up compiles both Low (opaque foliage, no world IBL/normal maps, cheap fog,
  canvas AgX) and Medium+ (IBL, normal maps, exponential fog, HDR target) material variants, including
  custom foliage depth programs and the viewmodel. Tier changes select these cached programs;
  every environment map (procedural bake and HDRI) is a PMREM of cube size `ENV_CUBE_SIZE` = 128
  (its texel size is compiled into lit shaders as defines). HDRIs are 512 × 256 for that reason.
- IBL: `tools/assets/build_env.py` turns Poly Haven HDRIs into 512 × 256 RGBE maps: sun inpainted
  (within 20° of it, anything brighter than the surrounding sky gets a smooth fill of that sky: the
  shadowed DirectionalLight is the sun, and the HDRI's sun elevation differs from the preset's, so
  a leftover sun would be a second highlight in glossy surfaces), other peaks clamped at 8× the
  median, rotated to the preset's sun azimuth, upper hemisphere normalised to mean luminance 1.
  Manifest and maps load under one 20 s deadline. The client scales each by `proceduralSkyMean(preset)` so a preset
  keeps the brightness it was tuned with; `envIntensity × exposure` stays the knob. Sunny, overcast
  and rain have HDRIs; dusk uses the sky bake (baked at exposure 1, lightning excluded).
- CAS (`render/sharpen.ts`, after AMD FidelityFX CAS) runs first in the tone-mapping pass on
  Medium+: a 5-tap cross on x/(1+x)-compressed HDR, clamped to the neighbourhood (no halos). Its
  strength is a uniform that follows the internal resolution (0 at 100 %, full at 50 %), updated in
  `PostPipeline.setSize`; at 0 it returns early. Nothing is added on Low.
- `DynamicResolution` adjusts the internal pixel ratio to hold 16.7 ms, with a 60% floor. In Auto,
  tiers drop after three seconds below 58 fps at the resolution floor.

### Practice match (offline vs bots)

`?practice` (Menu › Practice vs bots) runs `server/src/practice/practiceHost.ts` — the authoritative `MatchSim` and behaviour-tree bots, stepped like `MatchRoom` — in a Web Worker (`practiceWorker.ts`, bundled by Vite from the server package). `client/net/practiceRoom.ts` exposes it as a `MatchRoomLink` (the same surface as the SDK `Room`), so `Game` treats it as a friend room that has already started: one human (`you`, the host), the room's messages, validated with the room's schemas. No socket, no latency, the real bots.
